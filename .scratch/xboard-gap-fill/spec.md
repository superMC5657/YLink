# YLink 功能补齐 · 对齐 Xboard 缺口（Spec）

> Status: ready-for-agent
> 日期: 2026-08-27（2026-08-28 筛选：按用户决策排除支付/优惠券等资金方向条目，见 §3 状态列与 §6 结论）
> 来源: YLink vs [cedar2025/Xboard](https://github.com/cedar2025/Xboard)（V2Board 系）功能对比盘点
> 范围: Xboard 有而 YLink 缺失或深度不足的功能，按优先级立项；YLink 独有能力（Tauri 桌面端/Go 栈/可观测性/代理审批）不在本文档范围

---

## 1. 背景与目标

YLink 已完成核心交易闭环（账户/套餐/订单/支付/订阅/邀请/工单/管理端 13 模块）并投入联调，但与 Xboard 相比缺少一批**商业化外围能力**与**管理端深度操作**：

- 缺失独立模块：礼品卡、佣金提现、多支付渠道、插件/主题/在线更新、Telegram 机器人、运维监控界面等；
- 已有但深度不足：统计报表、批量操作、CSV 导出、手动标记支付等。

本 spec 的目标是逐项补齐这些缺口，形成与 Xboard 对等（或按商业场景取舍）的能力矩阵。

## 2. 对比口径

- 功能清单来源：Xboard `app/Http/Controllers/V1|V2` 全部控制器方法、`v2_*` 数据表、`plugins-core/` 支付插件目录、`theme/` 主题机制，对照 YLink `server/internal/router/router.go` 全量端点、`src/views` 前端页面、`server/migrations` 表结构。
- 优先级口径：P0 = 直接影响商业变现与营收闭环；P1 = 明显提升运营效率与数据决策；P2 = 生态/体验类，成本高、可缓排。

## 4. 需求明细

### ~~F01 礼品卡/兑换码系统（P0）~~

> **2026-08-28 筛选结论：不做。** 卡密兑换余额/套餐属资金收款变体，随支付/优惠券方向整体排除；若未来重启营销发卡需求再重估。

**现状**：YLink 无任何卡密能力。Xboard 具备完整 GiftCard 模块（模板 CRUD、批量生成、CSV 导出、启停、用量统计；用户端 check/redeem/history/detail/types）。

**目标行为**：
1. 管理端：礼品卡模板 CRUD（面额、周期、使用限制）；批量生成卡密（数量、前缀规则）；导出 CSV；启用/停用；用量与兑换统计（张数、金额、剩余）。
2. 用户端：输入卡密兑换（按面额充值余额，或直接开通套餐）；兑换历史；卡密类型查询。
3. 面向场景：代理/分销渠道发卡、线下售卖、活动赠送。

**涉及模块**：`server`（新表 `gift_card_templates`/`gift_cards`/`gift_card_usages`，服务、handler、路由）、`src/views`（管理端 + 用户端页面）、`mock`、`docs/api`。

**验收要点**：
- 批量生成幂等（重复提交不产生重复卡密）；卡密一次性兑换（行锁防并发双花）；兑换后余额变动入流水；停用卡密不可兑换。
- 管理端 CSV 导出字段与 `docs/api` 契约一致。

### ~~F02 佣金提现（工单提现）~~

> **2026-08-28 筛选结论：不做。** 提现属资金方向，随本次筛选排除。

**现状**：YLink 佣金只能划转为余额（`POST /invite/transfer`），无法提现。

**目标行为**：
1. 系统设置：提现开关（可关闭）、提现方式白名单（如 USDT-TRC20/支付宝/银行卡，可配置）、最低提现额、每次/每日限额。
2. 用户端：工单新增「佣金提现」类型（或独立提现入口）；提交时填提现方式+收款账号；校验佣金余额 ≥ 最低提现额；系统自动生成提现工单并**冻结/扣减**对应佣金。
3. 管理端：工单列表区分提现类型，可标记「已打款」完成提现；拒绝则佣金退回。

**涉及模块**：`server`（ticket 类型扩展、佣金冻结字段、设置项）、工单前端、管理端工单页、`docs/api`。

**验收要点**：
- 拒绝/关闭提现工单必须自动退回冻结佣金（状态机与退款一致，防资损）。
- 重复提交相同提现被防重/限额拦截。

### ~~F03 多支付渠道接入~~

> **2026-08-28 筛选结论：不做。** 支付方向，随本次筛选排除；现有 `pkg/payment.Driver` 注册表机制保留，后续按需单独评估。

**现状**：仅易支付驱动（`epay_alipay`/`epay_wxpay`）+ 余额支付。Xboard 有 AlipayF2f、Btcpay、Coinbase、CoinPayments、Epay、Mgate、Stripe。

**目标行为**：
1. 支付抽象层增加驱动注册表扩展能力（已具备 `pkg/payment.Driver` 接口，新增驱动即可）。
2. 优先接入：支付宝当面付（AlipayF2f，国内主要市场）、USDT 类（Coinbase/CoinPayments/Btcpay 三选一，海外/匿名场景）。
3. 管理端支付配置页：动态启停渠道、配置密钥、排序、手续费展示；用户端订单页展示可用支付方式（`/config` 已下发支付方式，扩展即可）。
4. `POST /payment/notify/{method}` 保持统一验签入口，各驱动自实现验签与查单。

**涉及模块**：`server/internal/pkg/payment`、settings、`docs/api`、前端订单/管理端设置页。

**验收要点**：
- 每种新渠道走通「下单 → 拉起 → 回调验签 → 开通续期」全链路；回调金额比对单位约定（分）不破。
- 未配置密钥的渠道自动隐藏，不影响其余渠道。

### F04 管理端统计报表增强（P1）

**现状**：仅有 `GET /admin/stat/overview` 单一概览。Xboard 有订单统计、节点排行（昨日/上次）、流量排行、用户留存、综合报表（getStats 等 8 组接口）。

**目标行为**（按落地成本递增）：
1. 订单统计：按日/周/月的订单数、营收（区分支付渠道）、退款额趋势图。
2. 节点排行：昨日流量 TopN、在线/离线状态。
3. 用户统计：注册趋势、套餐分布、活跃/沉睡用户。
4. 流量排行：用户流量消耗 TopN、节点流量分布。

**涉及模块**：`server`（统计聚合 SQL + 新端点）、前端新增「报表」管理页面、`docs/api`。

**验收要点**：聚合口径与 `traffic_logs`/`orders` 数据一致；时间范围参数化（默认近 30 天），避免全表扫描（走索引/物化统计）。

### ✅ F05 用户管理增强（P1）

> **2026-08-28 已完成 ✅**：CSV 流式导出（`GET /admin/users/export`，每批 500 + BOM）、批量操作（`POST /admin/users/batch`，ban/unban/adjust_balance 含负值保护与失败原因汇总）、管理端发邮件（`POST /admin/users/mail`，mail_logs 留痕，迁移 0005）、重置订阅密钥（`POST /admin/users/{id}/sub-token/reset`，复用用户端缓存清理）；前端 AdminUsersView 多选/批量工具栏/导出/邮件弹窗/行内重置订阅。

**现状**：管理端用户仅有列表/编辑/调余额/封禁。

**目标行为**：
1. CSV 导出（按筛选结果，字段：邮箱/余额/佣金/套餐/到期/流量/注册时间/邀请人）。
2. 批量操作：批量封禁/解封、批量调整余额（含负值保护）、批量发送通知。
3. 站内信/邮件：管理端向指定用户发邮件（复用 SMTP，记录发送日志）。
4. 重置用户订阅密钥（Xboard resetSecret 等价，YLink 已有 `POST /servers/:id/node-key/reset` 的节点侧，补用户侧）。

**涉及模块**：`server` admin 端点扩展、`src/views/admin/AdminUsersView.vue`、`docs/api`。

**验收要点**：导出走流式/分页防内存峰值；批量操作有结果汇总（成功数/失败原因）。

### F12 Telegram 机器人集成（P2）

**现状**：用户表仅存 `telegram_id`，无机器人交互。

**目标行为**（最小闭环）：
1. 管理端配置 bot token + webhook（`setTelegramWebhook`）。
2. 用户绑定/解绑（发送 `/bind <验证码>` 给 bot，或用户端填入 chat id）。
3. 通知推送：到期/流量提醒邮件的同时推 Telegram（复用现有 remind 定时任务的分发层）。

**涉及模块**：`server`（telegram 客户端 + webhook 端点 + 绑定流程）、`ProfileView.vue`、设置页、`docs/api`。

**验收要点**：webhook 签名校验；解绑后立即停止推送；推送失败不影响主流程（降级记日志）。

### F13 快速登录（邮箱一键登录）（P2）

**现状**：注册/登录/找回均需密码或验证码重置，无「免密登录」。

**目标行为**：`POST /auth/mail-login`：用户提交邮箱 → 发送一次性登录链接（含短期 token，单次有效）→ 点击即登录并签发 JWT；与快速登录 URL 生成（客服代登）共用 token 机制，仅限管理员生成。

**涉及模块**：`server` auth 扩展、`LoginView.vue`、`docs/api`。

**验收要点**：token 单次使用、短时效（如 10min）；被代登用户会话版本号 bump，防 token 泄露后持续有效。
